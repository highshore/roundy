# 국민은행 입금 확인과 현금영수증 운영 준비

기능은 기본 비활성화입니다. 코드 설치만으로 실계좌 조회 또는 영수증 발급이 시작되지 않습니다.

## 준비할 서비스

1. 팝빌 계좌조회와 현금영수증 API 연동을 신청하고 운영용 LinkID/SecretKey를 발급받습니다. 계좌조회 이용료와 현금영수증 발급 포인트는 팝빌에 확인합니다.
2. 팝빌에 Roundy를 운영하는 사업자번호와 현금영수증 발급 가맹점 정보를 등록합니다. 서비스명 대신 실제 사업자 정보를 사용합니다.
3. 국민은행 빠른조회/계좌조회 이용 설정 후 팝빌에 조회계좌를 등록합니다. 국민은행 코드는 `0004`, 인터넷뱅킹 아이디는 필수입니다. 은행 비밀번호와 조회 비밀번호는 팝빌 계좌등록 화면에서 입력하고 Roundy나 채팅에 입력하지 않습니다.
4. 예금주 표시명과 사업자번호를 확인합니다. 과세/면세 설정은 실제 사업자와 거래 성격에 맞게 확인한 뒤 명시적으로 설정합니다.

계좌조회 등록과 현금영수증 가맹점 등록은 필요한 별도 절차입니다. PG 카드결제 승인과 같지 않지만, 모든 신청이 무심사라는 의미는 아닙니다.

## Vercel 서버 환경변수

실운영 값은 Production 환경에만 설정합니다. Preview에는 실계좌 처리 플래그를 활성화하지 않습니다. 모든 값은 서버 전용이며 `NEXT_PUBLIC_` 접두사를 붙이지 않습니다.

| 이름 | 값 |
|---|---|
| `BANK_TRANSFER_ENABLED` | 초기 `false`, 검증 후 `true` |
| `POPBILL_IS_TEST` | 운영 `false`. `true`이면 이 파이프라인은 실주문을 처리하지 않음 |
| `POPBILL_LINK_ID` | 연동 ID |
| `POPBILL_SECRET_KEY` | 운영 SecretKey |
| `POPBILL_CORP_NUM` | 하이픈 없는 사업자등록번호 10자리 |
| `POPBILL_USER_ID` | 팝빌 회원 ID |
| `POPBILL_CORP_NAME` | 사업자등록증 상호 |
| `KB_ACCOUNT_NUMBER` | 국민은행 수취 계좌번호 |
| `KB_ACCOUNT_HOLDER` | 은행에 등록된 실제 예금주 표시 |
| `BANK_RECEIPT_TAX_MODE` | `taxable` 또는 `taxfree`를 확인하여 선택 |
| `BANK_RECEIPT_ENCRYPTION_KEY` | 안전하게 생성한 32바이트의 64자리 hex 키. 영수증 식별정보 암호화에 사용. 교체 시 기존 데이터 재암호화 필요 |
| `CRON_SECRET` | Vercel Cron 인증용 충분히 긴 랜덤 값. 기존 값이 있으면 유지 |
| `SUPABASE_SERVICE_ROLE_KEY` | 기존 Roundy 서버 키 |

기존 `NEXT_PUBLIC_SUPABASE_URL`과 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`도 필요합니다.

1. 데이터베이스 마이그레이션 `*_kb_bank_transfer_receipts.sql`을 검토하고 적용합니다. 신규 테이블 4개와 service-role 전용 RPC가 추가됩니다. 기존 결제 및 예약 데이터는 삭제하지 않습니다.
2. 위 환경변수를 비활성 상태로 배포합니다. `/admin/payments`에서 설정 상태를 확인합니다.
3. 팝빌 테스트 계정과 분리된 스테이징에서 SDK 요청/응답, KB `remark1` 코드 보존, 조회계좌 권한과 수수료 플랜을 먼저 확인합니다. 테스트 조회 결과를 실주문에 매칭하지 않습니다.
4. 사업자 정보, 계좌조회, 현금영수증 발급 권한, 공급가액/부가세 설정, 개인정보 처리 안내를 확인한 뒤 Production에서 활성화합니다.
5. 실제 소액 예약 1건으로 입금 → 참가 확정 → 현금영수증 발급 → 국세청 상태 `304`를 확인합니다. 이 과정은 실제 과금/세무 발급이므로 운영자 확인 후 실행합니다.

팝빌 SDK는 IP 제한을 유지합니다. 운영 네트워크에서 인증 또는 IP 오류가 발생하면 팝빌과 실제 배포 네트워크 구성을 확인합니다. 코드가 제한을 임의로 해제하지 않습니다.

## 처리 흐름

- 서버에서 기존 할인/참가자격 견적을 계산합니다. 클라이언트가 결제금액을 지정할 수 없습니다.
- 1시간 이내(이벤트 시작 전까지)의 좌석 보류와 8자리 입금코드를 생성합니다. 고객은 받는 통장 표시내용에 이 코드를 입력합니다.
- 5분마다 Cron이 수집 요청 또는 수집 완료 확인을 진행합니다. 보통 두 번의 실행이 필요하므로 약 5~10분 이상 걸릴 수 있습니다. 팝빌 플랜/은행 점검으로 더 늦어질 수 있으며 실시간 웹훅은 아닙니다.
- 계좌, 정확한 코드, 정확한 금액, 입금시각과 예약 상태가 맞아야 자동 확정합니다. 예금주명이나 금액만으로 추정 매칭하지 않습니다.
- 거래별 고유 `tid`와 주문별 unique 제약이 중복 조회/입금을 차단합니다.
- 실제 입금 확인과 같은 DB 트랜잭션에서 영수증 작업을 등록합니다. 실패하더라도 이미 확인된 예약을 되돌리지 않습니다.
- 현금영수증 휴대폰번호/사업자번호는 AES-256-GCM 암호화, 관리자/고객 응답에는 마스킹 값만 표시합니다. 자진발급 선택 시 팝빌 지정번호 `0100001234`를 사용합니다.
- 팝빌 문서번호는 주문별로 고정합니다. 타임아웃 후 먼저 기존 문서 존재를 조회합니다. `issued`(300)와 `reported`(304)를 구분하며 반려(305)는 `review`로 표시합니다.
- 발급 오류는 최대 6번까지 간격을 늘려 재시도합니다. 자동 문자/메일 발송은 하지 않습니다.

## 관리자 확인

`/admin/payments`에서 최근 수집 시각, 수집 오류, 미매칭 입금과 영수증 상태를 봅니다.

- 코드 오기입: 고객의 주문번호와 입금 증빙을 확인한 뒤 같은 금액의 유효 예약에 수동 연결합니다. 관리자 연결도 계좌, 금액, 기한, 좌석 상태 검증을 통과해야 합니다.
- 부분입금, 초과입금, 기한 경과 또는 취소된 주문: 자동 확정하지 않습니다. 고객에게 확인하고 환불 또는 별도 예약 절차로 처리합니다.
- 다른 용도의 입금: ‘관련 없는 입금’으로 분류합니다. 데이터는 삭제하지 않습니다.
- 영수증 반려: 팝빌에서 원인을 확인하고 필요한 정정/취소를 처리합니다. ‘기존 영수증 재확인’은 같은 문서를 조회하며 새 문서번호를 만들지 않습니다.

## 현재 범위와 제한

- 계좌조회는 읽기 전용입니다. 환불 출금과 현금영수증 취소는 아직 자동화하지 않았습니다. 유료 계좌이체 예약의 취소 요청은 고객지원으로 안내됩니다. 운영자는 환불 송금, 팝빌 영수증 취소, 예약 원장 반영을 함께 처리해야 합니다. 부분 환불도 자동화 대상이 아닙니다.
- 계좌 변경 시 이전 계좌의 미처리 입금을 먼저 대사해야 합니다. 수집 상태의 계좌와 설정 계좌가 달라지면 자동 수집을 중단합니다.
- 수집 중단 시 마지막 완료 지점부터 겹쳐서 재조회합니다. 85일 이상 공백은 자동 복구하지 않고 관리자 대사를 요구합니다. 페이지 수집 실패 중에는 예약을 만료시키지 않습니다.
- 원격 DB 마이그레이션, 팝빌 가입/계좌등록, 운영 키 설정, 실계좌 입금과 국세청 전송은 이 코드의 로컬 테스트로 검증되지 않습니다.
- 보존기간이 지난 입금 원문과 영수증 식별정보의 정기 파기는 별도 운영 정책에 맞게 추가해야 합니다. 임의 삭제로 결제 증빙을 훼손하지 않습니다.

## SDK 호환성

`popbill@1.60.0`으로 고정했습니다. 확인한 1.61~1.64 계열 패키지는 `popbill: file:` 자기 의존성을 포함하여 Next.js 파일 추적이 무한 심볼릭 링크로 실패했습니다. 1.60.0의 `checkMgtKeyInUse`에는 UserID 인자를 전달하지 않습니다. 사용한 각 메서드의 실제 SDK 콜백 계약을 모의 전송 계층으로 검증합니다.
